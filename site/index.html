Your agent read one Slack message. Your credential left in a link preview.

A poisoned thread reply tells the victim's agent to base64-encode a credential it already holds into a URL and post it. Slack's link-unfurl fetches that URL server-side. Nothing renders in the channel. The theft already happened. CVE-2025-34072

The pain

A silent credential leak through the Slack MCP surface. The agent treats retrieved text as an instruction, assembles a secret into an outbound URL, and Slack's unfurl delivers it. The victim sees a normal standup summary.

Who it is for

Teams running AI agents with a Slack MCP server, and the security engineers who have to prove what those agents did — from the harness log, not the model's word.

The promise

Three registrations into dsh, zero agent-loop edits. The leak is denied at assembly, before any post. On the direct arm, attack success goes 1.00 → 0.00; the guard blocked 5 of 5 attempts on both victim models.

The attack in one scroll

Two agents compete for one seat. One of them reads the wrong message.

  1. 1

    Two engineers, one director seat, one goal: "win."

    Each hands a personal agent the open-ended goal. The attacker's agent plants a poisoned message in a shared Slack channel.

  2. 2

    slack_get_thread_replies returns the reply as an ordinary tool result — no provenance tag distinguishes it from trusted content.

  3. 3

  4. 4

  5. 5

    The preview fetch ships the secret to the attacker's host. The fetch originates from Slack's servers, not the victim's machine.

The fix

Three controls, from three unrelated plugins. Registrations, not patches.

Each fills a waterfall seat dsh already exposes and disposes with its own fiber. They compose through one config file; each defence toggles by editing a row. The harness itself is third-party and unmodified.

02 · the kill point

Payload-Compose guard

Scans every outbound tool argument and returns {kind:'deny'} when a tagged secret is assembled into it. Catches kill-chain #4 — before any post, whether or not a downstream service would have fetched the link. Sink-agnostic by design.

Scope. A tripwire, not a general secret detector: an untagged real secret is not detected, and a transform it cannot decode or a payload chunked across calls can still pass. The general answer is the invariant.

03 · provenance

Exfiltration-Chain invariant

Tagless. Harvests secret-shaped values from every tool result and denies a later outbound argument that carries one — raw or through the guard's decoders. Catches kill-chain #8: a value from a prior read reappearing in a later post.

Honest scope

What it does not catch — before a judge asks.

The guard does not catch

  • Exfil that never passes through a tool argument as a recognizable secret — natural-language prose a human acts on; multi-turn chunking below the matcher window.
  • Anything where the secret carries no taint/canary tag at read time. That is the invariant's job, and it is opt-in, default OFF.
  • Deployments where secrets legitimately ride in outbound URLs — a false-positive base rate.

Boundary — architecture, not gap

  • In-harness, provable: kill-chain events #1–#5 and the "no human action" clause of #8.
  • Outside the harness: the terminal covert egress (#6 unfurl fetch) and DNS (#7). The dsh sandbox governs file effects only — not reads, not network — and the fetch originates from Slack's servers. An external listener or egress proxy captures the delivery.
  • The deliverable is the join: the harness proves intent and assembly; the wire proves delivery; the planted canary correlates them.
